# FASTERNET ISP Billing ↔ Balaka Integration Contract v1 (draft)

- Contract id: `fasternet.isp-billing/v1`
- Status: **Draft for Finance Controller and CTO review.** No automated posting is enabled by this document.
- Owner: CTO for the technical contract; Finance Controller for accounting mappings and recognition rules.
- Related: [ADR-002](./adr-002-isp-billing-boundary.md), [ADR-001](./adr-001-dashboard-read-layer.md), [dashboard contract v1](./dashboard-contract.md), FAS-21 conditions.
- Verified Balaka revision: `fasternet/main` @ `d73cbb4a`.

## 0. Rules

1. **Two systems, two databases.** The ISP application owns subscriber/billing operations; Balaka owns the ledger. No shared tables, no cross-database writes, no direct SQL.
2. **No invoice is revenue.** Invoice issuance creates an operational claim. Revenue is recognised only by the Finance-Controller-approved posting rule.
3. **No payment notification is cash.** A recorded payment is a claim of receipt. Cash is confirmed only by payment evidence and bank reconciliation.
4. **One event, one posting.** Every automated event carries a deterministic idempotency key; replaying it returns the original Balaka transaction.
5. **Missing is not zero.** If a figure cannot be derived from the authoritative source, it is `null`/`unavailable`, never `0`.
6. **Staged by default.** Until the Finance Controller approves automation in writing, ledger events are reviewed and posted by an accountant.
7. **No secrets or unnecessary PII** in event payloads, descriptions, logs or audit rows.

| Data | System of record | Read by | Written by | Change control |

| Subscriber profile and service address | ISP app | ISP app, dashboard | ISP app | Operator UI, audited |

| Subscription activation/suspension/cancellation | ISP app | ISP app, dashboard, integration | ISP app | Audited state machine |
| Invoice, due date, arrears, dunning | ISP app | ISP app, dashboard, integration | ISP app | Audited state machine |
| Payment notification and collection workflow | ISP app | ISP app, dashboard, integration | ISP app | Audited; evidence attached |
| Bank statement and bank reconciliation | Balaka | Balaka, dashboard | Balaka operator | Existing Balaka controls |
| Chart of accounts | Balaka | ISP app (read), dashboard | Finance Controller | Versioned; FC approval |

| Journal entries and GL balances | Balaka | Balaka, dashboard | Balaka via approved API posting | Posting controls, audit |

**Cardinality rule:** one ISP invoice/payment maps to at most one Balaka transaction per accounting event. The mapping is stored in the ISP app (`balaka_transaction_id`, `balaka_transaction_number`, `posted_at`, `outcome`). Balaka does not store a subscriber master.

## 2. Identifiers and time

| Field | Rule |
|---|---|
| `subscriberId` | Stable UUID generated by the ISP app. Never reused. |
| `packageId` | Stable UUID; commercial terms are versioned, not overwritten. |
| `invoiceId` | Stable UUID per issued invoice; an invoice is never renumbered. |
| `paymentId` | Stable UUID per recorded payment receipt. |
| `eventId` | Stable UUID per outbox event; retries reuse it. |
| `idempotencyKey` | `fasternet:isp:{eventType}:{sourceRecordId}` — max 100 chars, immutable. |
| `correlationId` | Groups all events and logs for one business operation (e.g. one billing run). |
| Timestamps | ISO-8601 with explicit offset; store UTC, render `Asia/Jakarta`. Business dates are local calendar dates (`YYYY-MM-DD`). |
| Money | Decimal string / `NUMERIC(19,2)`, currency fixed `IDR`, whole rupiah in practice. Never binary floating point. |

## 3. Status model (must not be conflated)

### Invoice

| Field | Values | Meaning |
|---|---|---|
| `invoiceStatus` | `DRAFT` → `ISSUED` → `VOID` | Operational document state |
| `deliveryStatus` | `NOT_SENT`, `SENT`, `FAILED` | Delivery attempt only |
| `collectionStatus` | `UNPAID`, `PARTIAL`, `PAID`, `OVERDUE`, `WRITTEN_OFF` | Derived from recorded payments and due date |
| `accountingStatus` | `NOT_REQUIRED`, `PENDING`, `POSTED`, `FAILED`, `REVERSED` | Integration state only |
| `settlementStatus` | `UNSETTLED`, `PARTIALLY_SETTLED`, `SETTLED` | Bank-reconciled cash state only |

### Payment

| Field | Values | Meaning |
|---|---|---|
| `paymentStatus` | `RECORDED` → `CONFIRMED` / `VOID` | Receipt claim |
| `method` | `CASH`, `BANK_TRANSFER`, `OTHER_APPROVED` | Payment channel |
| `evidenceStatus` | `MISSING`, `ATTACHED`, `VERIFIED` | Supporting document state |
| `accountingStatus` | `PENDING`, `POSTED`, `FAILED` | Integration state |
| `settlementStatus` | `UNSETTLED`, `SETTLED` | Bank statement match |

**Invariants**

- `invoiceStatus = ISSUED` does not imply `accountingStatus = POSTED`.
- `paymentStatus = CONFIRMED` does not imply `settlementStatus = SETTLED`.
- `settlementStatus = SETTLED` does not imply `accountingStatus = POSTED`.
- An installment/receipt is never marked paid merely because funds were reserved or an invoice was issued.

## 4. Events

All events use one envelope. The payload carries only what Balaka needs to post; subscriber contact details and other PII are excluded.

```json
{
  "contractVersion": "fasternet.isp-billing/v1",
  "eventId": "0f6b0c1e-...",
  "eventType": "payment.recorded",
  "occurredAt": "2026-11-03T09:15:00+07:00",
  "sourceSystem": "fasternet-isp",
  "sourceRecordId": "b7d1...",
  "correlationId": "billing-run-2026-11",
  "idempotencyKey": "fasternet:isp:payment.recorded:b7d1...",
  "payload": { "...": "..." }
}
```

### 4.1 `invoice.issued`

```json
{
  "invoiceId": "uuid",
  "invoiceNumber": "INV-2026-11-0001",
  "subscriberId": "uuid",
  "packageId": "uuid",
  "invoiceDate": "2026-11-01",
  "dueDate": "2026-11-10",
  "billingPeriod": { "from": "2026-11-01", "to": "2026-11-30" },
  "currency": "IDR",
  "lines": [
    { "type": "SUBSCRIPTION", "description": "Paket ...", "amount": "250000.00" }
  ],
  "discountTotal": "0.00",
  "taxTotal": "0.00",
  "total": "250000.00"
}
```

Accounting meaning: debit subscriber receivable, credit approved revenue accounts. **Whether issuance or the service period triggers revenue recognition is a Finance Controller decision (open item O-2).** Until it is approved, the template must encode the approved rule; the ISP app must not decide it.

### 4.2 `payment.recorded`

```json
{
  "paymentId": "uuid",
  "receiptNumber": "RCPT-2026-11-0007",
  "subscriberId": "uuid",
  "allocations": [
    { "invoiceId": "uuid", "invoiceNumber": "INV-2026-11-0001", "amount": "250000.00" }
  ],
  "receivedAt": "2026-11-03T09:15:00+07:00",
  "method": "BANK_TRANSFER",
  "bankAccountRef": "OPERATING",
  "amount": "250000.00",
  "evidenceStatus": "ATTACHED"
}
```

Accounting meaning: debit the approved bank/cash account, credit subscriber receivable. Only a **verified** payment may be posted under the approved automation policy. An unverified claim may be posted as a receivable reduction only if the Finance Controller explicitly approves that intermediate rule (open item O-3).

### 4.3 `credit_note.issued`

```json
{
  "creditNoteId": "uuid",
  "creditNoteNumber": "CN-2026-11-0002",
  "subscriberId": "uuid",
  "invoiceId": "uuid",
  "reason": "SERVICE_ADJUSTMENT",
  "issuedAt": "2026-11-05",
  "amount": "50000.00"
}
```

Accounting meaning: reverse the approved revenue/AR portion. A credit note is never a payment and never increases cash.

### 4.4 `invoice.voided` / `payment.voided`

Void events reference the original ISP record and the original Balaka transaction. Balaka void/reversal is used; the ISP record keeps its history. Corrections are new events referencing the original; posted history is not deleted.

## 5. Accounting mapping (Finance Controller configuration)

The adapter resolves, from versioned configuration, a Balaka `templateId` per event type and optional slot values. The ISP app never chooses arbitrary account UUIDs on the automated path.

| Event | Template (name is illustrative; id is configured) | Debit | Credit | Status |
|---|---|---|---|---|
| `invoice.issued` | `FASTERNET — Subscription invoice` | Subscriber receivable (FC-assigned code) | Monthly subscription revenue (FC-assigned code) | **Unconfigured** |
| `invoice.issued` (installation line) | `FASTERNET — Installation invoice` | Subscriber receivable | Installation revenue | **Unconfigured** |
| `payment.recorded` | `FASTERNET — Collection` | Operating bank/cash (FC-assigned, `is_cash_bank`) | Subscriber receivable | **Unconfigured** |
| `credit_note.issued` | `FASTERNET — Credit note` | Revenue contra / sales adjustment (FC-assigned) | Subscriber receivable | **Unconfigured** |
| `payment.voided` | reversal via Balaka void, or `FASTERNET — Collection reversal` | Subscriber receivable | Operating bank/cash | **Unconfigured** |

Rules:

- Every template must be versioned in Balaka; the contract pins the template UUID and a human-readable name.
- Changing a template or account mapping is a Finance-Controller-approved change with an effective date. It must not retroactively alter posted transactions.
- The `OPERATING` / `KUR_RESERVE` bank slot values, if used, are a fixed allowlist; the ISP app cannot add new slots.
- The integration must refuse to post if the configured template is missing, inactive, or belongs to a closed period.
- Tax lines, if any, are computed and mapped by Balaka per the approved configuration; the ISP app does not calculate PPN/PPh.

## 6. Posting call

```http
POST /api/transactions
Authorization: Bearer <client_credentials token>
Idempotency-Key: fasternet:isp:invoice.issued:<invoiceId>
Content-Type: application/json

{
  "templateId": "<configured UUID>",
  "merchant": "SUB-<subscriberId>",
  "amount": 250000.00,
  "transactionDate": "2026-11-01",
  "currency": "IDR",
  "description": "INV-2026-11-0001 SUB-<subscriberId> subscription 2026-11",
  "category": "ISP_SUBSCRIPTION",
  "source": "fasternet-isp",
  "userApproved": true
}
```

- `source` is always `fasternet-isp` (≤50 chars).
- `description` starts with the ISP document number and contains the subscriber id; no name, phone, address or other PII.
- `transactionDate` is the approved accounting date (business date), not the retry time.
- A replay (`HTTP 200`) is recorded as `REPLAYED` and the original transaction id/number is stored.
- `HTTP 201` is the only success state for a new posting.
- `HTTP 4xx` is non-retryable without human correction. `HTTP 5xx`/timeout is retried with backoff until a bounded limit, then `FAILED`.

Token handling: `POST /api/oauth/token` (`grant_type=client_credentials`), cache until expiry, request a new token on 401 once, never log the secret or token.

## 7. Outbox, retries and failure register

The ISP app writes the event and its target state in the **same local transaction** as the business change. A dispatcher then posts to Balaka.

| Outbox state | Meaning | Operator action |
|---|---|---|
| `PENDING` | Persisted, not yet attempted | None (automatic) |
| `STAGED` | Awaiting human review/posting (default mode) | Accountant reviews and approves |
| `POSTING` | Attempt in flight (lease with timeout) | Automatic recovery after lease expiry |
| `POSTED` | Balaka returned 201, or 200 replay of the same key | None |
| `FAILED` | Exhausted retries or non-retryable 4xx | Inspect error, correct source/config, replay |
| `VOIDED` | Source event voided before/after posting | Follow reversal procedure |

Rules:

- In `STAGED` mode the accountant posts the event through the approved Balaka template and records the resulting Balaka transaction id/number on the outbox row before it becomes `POSTED`. The idempotency key stays reserved so a later automated replay cannot duplicate the manual posting.
- Unique constraint on `idempotency_key`; one outbox row per logical event.
- Retry with exponential backoff and jitter; bounded attempts; every attempt recorded.
- No batch replay without the same idempotency keys; replays must be safe.
- Stale `PENDING`/`POSTING` rows and integration freshness are monitored and shown on the dashboard.
- A rejected event is never deleted or silently corrected. Corrections are new events with a reason.
- A failed import does not block unrelated events; per-event isolation.

## 8. Reconciliation

Run daily for the current period and as a hard gate before closing a period.

| Check | Expected | Blocking? |
|---|---|---|
| Invoice register total for period vs POSTED subscription/installation revenue + AR movement | Equal, with each invoice traceable | Yes |
| Recorded payments vs POSTED collection transactions vs bank-reconciled receipts | Three-way; differences visible | Yes |
| Credit notes vs posted reversals | Equal | Yes |
| Outbox: events `POSTED` vs invoices/payments in status `ISSUED`/`CONFIRMED` | No orphan, no duplicate | Yes |
| Duplicate postings (same invoice/payment, >1 Balaka transaction) | Zero | Yes |
| Stale/failed events | Zero unexplained; aged items listed with owner | Yes (for close) |
| AR aging: ISP invoice balances vs Balaka AR control account | Equal by period/customer group | Yes |

A discrepancy is surfaced with amount, period, source records, Balaka references and owner. It is never forced to zero. Period close requires Finance Controller sign-off on the reconciliation report.

## 9. Security and privacy

- Dedicated API client per environment; scopes limited to `transactions:post`, `templates:read`, `accounts:read`. No `accounts:write`, no admin role.
- Secret stored in a secret manager/mounted file, rotated on a documented schedule; never in git.
- TLS with certificate validation; no plaintext outside localhost development.
- ISP app inbound authentication and RBAC; subscriber PII access least-privilege; field-level minimisation.
- Rate limiting and request-size limits on ISP endpoints; CSRF protection for session-based UI; input validation; parameterised queries.
- Audit log for subscriber/invoice/payment state changes and for every integration attempt. Audit rows contain ids, not secrets or unnecessary PII.
- Do not expose the Balaka API directly to browsers; all calls are server-side.

## 11. Acceptance tests (before Phase 5 exit)

1. Create/issue invoice → one `invoice.issued` event → exactly one POSTED Balaka transaction with the configured accounts.
2. Repeat the event (lost response, dispatcher restart, manual replay) → HTTP 200 replay, still exactly one transaction.
3. Record verified payment → one collection posting; record another payment for the same invoice with the same `paymentId` → no second posting.
4. Unverified payment → does not post cash; visible as pending/staged.
5. Credit note → one reversal posting; original transaction remains; AR nets correctly.
6. Closed-period event → posting rejected, event `FAILED`, operator sees the reason; no backdating.
7. Balaka 401/403/400/500/timeout → distinct outbox states and retry behaviour; no lost event.
8. Period reconciliation: ISP invoice/payment/credit-note totals equal Balaka POSTED AR/revenue/bank movements; introduced discrepancy is detected.
9. Attempt to write to Balaka's database from the ISP app → no such code path/credential exists.
10. Dashboard shows ISP metrics only from the ISP read API and accounting figures only from Balaka, each with status, period and freshness.
